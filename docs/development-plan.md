# AI 宠物管家开发计划

## 1. 计划原则

- **先验证后扩展**：先在微信小程序验证核心闭环，再扩展原生 App。
- **先核心后智能**：宠物档案、记录和提醒无需依赖 AI 也应完整可用。
- **跨端边界清晰**：业务领域、基础设施与平台能力解耦，避免微信实现污染共享逻辑。
- **安全隐私前置**：权限、数据生命周期和 AI 安全在开发前完成设计，不作为上线前补丁。
- **以阶段门禁控制范围**：每阶段通过验收后再进入下一阶段，不以未经评审的日期承诺代替质量标准。

## 2. 建议架构方向

正式初始化工程时，建议按职责组织，而不是按单个平台堆叠代码：

```text
src/
├── app/             # 应用启动、路由、全局装配
├── features/        # 按业务域组织的功能模块
├── domain/          # 平台无关的实体、规则与用例
├── components/      # 跨功能复用的展示组件
├── services/        # API、AI、存储等接口及实现
├── adapters/        # 微信/iOS/Android 平台能力适配
├── store/           # 客户端状态组织
├── styles/          # 设计令牌与全局样式
├── types/           # 公共类型声明
└── utils/           # 无业务归属的纯工具
```

此结构是后续技术设计的候选方案，并非要求当前阶段创建空代码目录。工程初始化前还需用 Taro 的实际多端能力验证原生 App 路线；若 App 端需要独立壳层，应继续共享领域包和服务契约，而非强行共享所有 UI。

## 3. 阶段拆分

### 阶段 0：产品与技术设计（当前）

**目标**：明确首期范围、用户路径和技术边界。

**工作项**：

- 整理产品需求、优先级、非目标和验收原则。
- 建立 `design/` 资料结构，后续补充信息架构、线框图和视觉规范。
- 调研 Taro 对微信小程序、iOS 和 Android 的支持边界。
- 设计领域模型、数据生命周期、权限申请和 AI 安全策略。
- 定义首期指标、埋点方案和风险清单。

**交付与门禁**：

- 产品需求评审通过，P0 范围无关键歧义。
- 核心流程原型可完成可用性走查。
- 技术方案明确跨端策略、状态管理、测试方案和数据边界。
- 隐私与医疗免责声明经过合规评审。

### 阶段 1：工程骨架与基础体验

**目标**：建立可持续开发、测试和发布的跨端工程基线。

**工作项**：

- 初始化 Taro + React + TypeScript 工程并启用严格类型检查。
- 配置代码检查、格式化、单元测试、提交检查和持续集成。
- 建立环境配置规则，确保密钥不进入客户端代码或版本库。
- 落地路由、错误边界、状态组织、服务接口和平台适配层。
- 建立设计令牌与基础组件，并完成微信开发者工具真机调试链路。

**交付与门禁**：

- 开发、测试和生产配置边界清楚，示例工程可在微信小程序端构建。
- 自动化检查稳定运行，基础组件具备状态与可访问性验证。
- 用最小技术样例验证共享领域逻辑及平台适配方式。

### 阶段 2：本地核心闭环（MVP）

**目标**：在暂不依赖登录和远端数据库的情况下验证核心体验。

**工作项**：

- 实现多宠物档案管理。
- 实现健康记录、时间线、筛选与编辑能力。
- 实现一次性及重复提醒、完成状态和应用内提醒列表。
- 完善空状态、异常状态、表单草稿与防重复提交。
- 开展真机功能、性能、无障碍和可用性测试。

**交付与门禁**：

- “建档—记录—提醒—回顾”完整闭环通过验收。
- 核心领域规则有单元测试，关键用户路径有集成或端到端测试。
- 本地数据升级策略经过验证，测试数据可安全重置。

### 阶段 3：云端同步与微信能力

**目标**：在安全方案确认后支持身份、可靠同步和微信触达。

**工作项**：

- 设计并实现后端 API、数据库、鉴权和权限模型。
- 经单独评审后实现微信登录、账号绑定与注销。
- 实现多端同步、幂等写入、冲突处理、备份和恢复策略。
- 按用户授权接入微信订阅消息。
- 实现数据导出、删除、审计与隐私设置。

**交付与门禁**：

- 安全评审、权限测试、数据迁移及故障恢复演练通过。
- 弱网、离线、重复请求与跨设备冲突场景具备确定行为。
- 登录拒绝、通知拒绝和账号注销路径通过验收。

### 阶段 4：AI 能力

**目标**：上线可评估、有边界、可反馈的 AI 辅助体验。

**工作项**：

- 通过服务端 AI 网关接入模型，禁止在客户端内置供应商密钥。
- 实现一般性问答、授权记录摘要、上下文范围控制和来源提示。
- 建立内容安全、紧急情况识别、拒答、限流、超时与降级机制。
- 构建离线评测集与人工抽检流程，监测质量、成本和延迟。
- 提供反馈、会话管理、数据使用说明及删除能力。

**交付与门禁**：

- 安全红队测试与医疗边界评审通过。
- 预设质量和延迟指标达标，失败时不影响核心记录功能。
- AI 数据保留、用户授权和供应商处理规则清晰可查。

### 阶段 5：iOS 与 Android 扩展

**目标**：复用稳定的领域能力，提供符合各平台习惯的原生应用体验。

**工作项**：

- 验证 Taro 构建方案；根据验证结果决定共享 UI 比例和原生壳层方案。
- 适配导航、权限、通知、媒体、存储、安全区和无障碍特性。
- 完善跨端同步、深链接、崩溃监控和灰度发布。
- 完成 App Store 与 Android 渠道的隐私、内容及上架检查。

**交付与门禁**：

- iOS、Android 的关键路径和跨端数据一致性通过真机测试。
- 平台特定体验符合审核政策，崩溃率与性能达到发布基线。
- 具备回滚、数据兼容和版本升级方案。

## 4. 横向质量工作

每个开发阶段均需持续执行：

- **测试**：领域单元测试、组件测试、关键路径端到端测试与真机回归。
- **可观测性**：不泄露敏感内容的错误、性能和业务指标监控。
- **安全**：依赖审计、密钥扫描、最小权限、接口鉴权和滥用防护。
- **隐私**：数据清单、用途说明、授权记录、保留期限和删除验证。
- **文档**：架构决策记录、接口契约、数据字典、发布及回滚手册。
- **跨端验证**：共享模块变更应评估微信、iOS 和 Android 的兼容影响。

## 5. 近期下一步

1. 评审并锁定 P0 需求，明确附件、离线和家庭共享是否进入首期。
2. 绘制核心用户流程和低保真原型，放入 `design/docs/`，验收截图放入 `design/screenshots/`。
3. 完成 Taro 多端技术验证，记录关键架构决策。
4. 定义领域模型、服务契约、隐私数据清单和测试策略。
5. 阶段 0 门禁通过后，再初始化工程依赖和代码目录。
